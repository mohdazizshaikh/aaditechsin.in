# V9.5 and V9.6 — safe publication and owner reporting (source only)

## Telegram business channel publishing
V9.5 supports one official Telegram business channel, text caption only. Facebook, Instagram, LinkedIn, YouTube, Google Business Profile, X, Threads and blog have creative draft formats but no live publishing adapters. WhatsApp messaging, social inbox, images/videos, reach metrics and paid promotions are not implemented. No automatic posting of a draft simply because it is approved.

- Apply additive 2026-11-24-v95.sql after V9.4 to isolated backed-up staging.
- Set up a separate business posting bot with only required rights to an approved test channel. Do not reuse owner bot token. Keep all social flags false until acceptance. Store actual negative numeric channel ID and token privately, never in Git, shell history or chat.
- Create a Telegram creative request, generate/import a draft, verify technical accuracy and approve exact revision. /socialtarget shows configured destination. Explicitly use /schedulepost TASK REV CHANNEL_ID YYYY-MM-DDTHH:MMZ (UTC, future, at most 30 days). /social reports state. /cancelpost ID cancels only queued posts.
- Private social-publish.php with --dry-run counts due rows without network; --run claims one due approved revision for exact configured channel. Pause blocks claim, not an in-flight request. Separate private lock. No auto retry of failed/ambiguous sends; interrupted sending is marked unknown after 15 minutes on next run. Verify actual channel before any new attempt. Changing target prevents queued old-target rows from being claimed.
- Uses official fixed Telegram Bot API sendMessage (https://core.telegram.org/bots/api#sendmessage), HTTPS verification, no redirects/proxy and bounded response. accepted requires HTTP 200, ok true, positive message_id and matching chat ID. That means provider acceptance, not audience reach/read. Unknown or rejection never counted as accepted. No network calls in CI.
- Actual token authorization, destination identity, post appearance, revocation and scheduling need live test-channel acceptance. Only then schedule cron. Never auto-retry ambiguous posts.

## Private owner notifications
V9.6 adds owner-only /errors, /notifications, /reporthistory, /notifydaily on|off and /notifyerrors on|off. Apply 2026-11-24-v96.sql. Default preferences ON but private reports_enabled OFF. Separate owner bot token and authorized private chat, same user ID and chat ID. Owner must initiate chat and test webhook first. Configure daily_after_ist (default 18:00 IST). Run private owner-notify.php --dry-run to inspect report availability and current recorded errors; --run attempts one daily day-to-date snapshot after configured time and one report for the last completed UTC hour only if discovery/publication errors were recorded. Cron not installed. No backfill for missed hourly periods. No continuous or every-event push yet. Monitoring intentionally stays active while growth paused, unless notification preferences or flags disabled. Both types deduplicated by period, not retried automatically after a failed/unknown attempt. Provider receipt does not mean owner read message. Use /reporthistory to reconcile. Full errors, telephony/email/social inbox/marketing performance monitoring are not implemented. SMTP dead rows are inventory, not sent/received communications.
