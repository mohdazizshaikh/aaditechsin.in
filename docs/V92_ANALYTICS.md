# V9.2 optional first-party analytics — source only

Seven public homepage/service/planner pages share the existing chat script entry point, which loads analytics.js only when the public analytics flag is true. The browser shows an explicit allow/off control and honors GPC/DNT. No tracking on portal, tracking-token pages or privacy page. No submission text, contact data, raw referrer URL/query, raw IP or raw user agent is stored in the analytics event table. Normal server logs are separate. Store a local preference and, only after consent, a random tab-session identifier and broad source category. Day-scoped keyed session hashes provide approximate consented tab-session counts, not humans or cross-day unique visitors. No fingerprinting.

## Event and report semantics
- page_view, service_interest (home service card/selector across all 14 categories), chat_open, call_click, email_click; page-level service labels on dedicated pages.
- Source is first observed broad tab channel: direct/search/social/email/referral/other, inferred from recognized UTM source or referrer. No full campaign ID, cross-source attribution or contact-to-session join. Real saved leads by intake path come directly from leads table (IST daily boundaries). Clicks never count as actual calls, sent emails or sales.
- Automation signals derive from webdriver or limited UA patterns. This is not bot/human classification. Non-JS/non-consenting requests are not represented. Hostinger access log analysis and GA4/Search Console connectors still pending.
- Exact origin, HTTPS, strict schema, day/event deduplication, 100-event/tab/day and 10,000-event/day storage caps. These are abuse safeguards, not a WAF. Adversarial events can still distort counts; report values as estimates. No report on public endpoint.
- Telegram /visitors, /pages, /services, /sources, /calls, /leads, /today, /health query database; no live bot connected. Actual calls, sent/received messages, social reach, full errors and outreach remain unconnected. No automatic daily delivery yet.
