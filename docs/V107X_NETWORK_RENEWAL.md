## Critical rotation and recovery protocol
Before exchange create a 0600 PROVIDER-exchange-attempt.json marker. After successful parsed response, persist the exact response in a separate 0600 PROVIDER-unverified-exchange.json file before scope/identity verification. These files are sensitive (the response contains credentials); never print, share, log or use as active config automatically. A missing response after an attempt is uncertain: the remote refresh token may already have rotated. Stop; reconcile provider state or reauthorize independently. An unverified response is not authorization and may contain an invalid or broader grant. No automatic retry, replacement or marker removal. On validated response and identity create the separate V10.7J-compatible PROVIDER-rotation-candidate.json. All three names block subsequent exchange until operator reconciliation. Use V10.7J HMAC review and separate authorized credential/grant activation; safely replace the old refresh token and update reviewed deadlines/generation only after independent validation, then archive/remove journals securely. No automatic activation. Disk failure, lost response, process crash or power loss can still leave ambiguous provider state; fsync of the file does not guarantee directory metadata durability. Do not claim distributed atomicity. Candidate creation does not prove publishing permission.
