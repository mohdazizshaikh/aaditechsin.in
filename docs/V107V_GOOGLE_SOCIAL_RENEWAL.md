# V10.7V — scheduled Google social OAuth replacement candidates

Baseline V10.7U f279d9761b4b444383f19016d03bae4f29bf4918. Its CI was running when development began. No schema changes (37 migrations, 49 tables, 39 pinned hashes).

## Scope
Automatic acquisition of short-lived replacement access tokens for Google Business Profile and YouTube from separately authorized offline refresh grants. Exact scope set: business.manage for Google Business; youtube.readonly plus youtube.upload for YouTube. These are powerful grants; owner must separately authorize the required operations and verify the provider's application policies. Reference: https://developers.google.com/identity/protocols/oauth2/web-server ; https://developers.google.com/my-business/content/implement-oauth ; https://developers.google.com/youtube/data/guides/authentication ; https://developers.google.com/identity/protocols/oauth2/scopes . No initial consent, refresh-token rotation, revoked-grant recovery or scope expansion. Candidate identity verification uses existing exact YouTube channel check and Google Business configured location-path access check, not proof of publish permission.

## Operator procedure
Enable existing growth/creative/social/provider and applicable media flags, oauth_lifecycle.enabled, rotation_review_enabled, automatic_candidate_enabled and the individual renewal provider enabled/authorized flags only on approved isolated staging. All new flags default false. Configure separate private offline grant client ID/secret/refresh token, exact reviewed target ID, fresh random grant generation, UTC grant review deadline (within 90 days), and canonical 0700 directory outside webroot. Stop all external workers and pause growth independently; do not edit config during the run. Existing active credential policy must be valid in shape and not revoked; old access token can be expired but must be structurally valid.

`php /PRIVATE/secure/maintenance/social-renew.php --check youtube`
`php /PRIVATE/secure/maintenance/social-renew.php --scheduled-run youtube`
Repeat for google-business. --check is local only. Owner may install private cron, for example every five minutes at separate offsets, while growth is paused and maintenance is authorized. No cron installed here. Candidate generation is due when the current access-token review deadline is within 15 minutes or expired. Existing candidate file stops new requests; inspect/remove or archive securely through operator procedure before a new run. No automatic deletion or overwrite. Do not leave cron running unattended during active publication.

Fixed Google HTTPS exchange; exact granted scope set, Bearer type, expiry and unchanged refresh-token grant required. Per-provider advisory lock, fresh grant/database/pause and clock checks, no DB transaction across HTTP, final pause row lock before private file creation. Expiry is min(provider expiry minus 60 seconds, reviewed grant deadline). A successful candidate is written to PROVIDER-rotation-candidate.json in the private directory (0600, non-overwriting). Contains live secret, never print/share/commit. Existing V10.7J oauth-rotation --plan and --verify accept this exact file schema via private stdin and reviewed HMAC. Independently review token scopes/expiry, then use separate authorized manual active credential rotation with fresh generation; no active credential mutation or automatic activation here. Candidate-file creation and DB transaction are not atomic; inspect state after any failure. A failed exchange or identity probe never triggers automatic retry inside the process. Neither local deadlines nor an identity check guarantees current access. No refresh secrets in logs.
